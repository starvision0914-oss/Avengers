대량(수천~수만 건) 상품명 최적화 작업을 API 키 없이 대화 세션 안에서 직접 처리할 때 쓴 방법. 사용자가 "API 키 대신 여기서 네가 진행해줘"라고 명시적으로 요청해 이 방식을 채택했고 잘 작동함.

## 핵심 원칙: 창작이 아니라 "스캔 후 예외처리"
- 전체를 하나하나 창작(rewrite)하려 하면 수만 건 규모에서 불가능. 대신:
  1. 금칙어/위험 키워드로 **먼저 스캔**해서 진짜 손봐야 할 항목만 추려낸다 (실측: 3,464건 중 26건, 15,395건 중 151+38건 정도로 실제 위험군은 전체의 1~5% 수준).
  2. 나머지 대다수(90%+)는 이미 클린한 상태 → 원본 유지가 정답인 경우가 많음. "다 바꿔야 한다"는 가정을 버릴 것.
  3. 애매한 브랜드/캐릭터 건은 hulk API의 detailContent(보통 이미지 1장)를 다운로드해 Read 툴로 직접 봐서 라이선스 판정(제조사·상품코드 명시 여부로 판단).
  4. 50byte 초과처럼 기계적으로 처리 가능한 문제(중복단어 제거+뒷부분 트림)는 스크립트로 일괄 처리.
  5. 카테고리 기반 키워드 추가처럼 "정답이 있는" 보강은 룰 기반으로 스케일링 가능하지만, **셀러의 카테고리 오분류가 섞여있을 수 있어** 카테고리-상품명 어휘 연관성 체크(같은 리프카테고리 다른 상품들과 토큰 겹치는지) 필터를 반드시 거칠 것 — 안 거르면 엉뚱한 키워드가 붙는 사고 발생(칫솔에 "작업 수공구" 붙는 식).

## 적용/실행 시 주의
- 실제 라이브 반영(hulk API PUT 등)은 되돌리기 어려운 작업 — 반드시 소량(5건) 테스트 후 전체 실행.
- 11번가는 `guard.preflight(wait=True)`로 락을 걸어야 함. verify/광고전략 등 다른 예약작업과 순번대기 발생할 수 있고 몇 시간 걸릴 수 있음 — 진행 중인 배치를 죽이지 말고 자동 대기하도록 설계.
- 속도(--sleep) 조정은 사용자에게 트레이드오프(계정 이상탐지 위험 vs 시간)를 명시하고 선택받을 것 — 확인 없이 임의로 빠르게 돌리지 말 것.
- **범위(트리밍만/키워드추가까지/상세페이지확인수준)를 시작 전에 한 번에 확정할 것** — 중간에 범위 추가되면 이미 실행 중인 배치와 충돌 방지 위해 어쩔 수 없이 2단계로 쪼개야 함(비효율).

## hulk API 실행 중 실측된 제약/함정 (2026-07-01~02, jinag7460 5,871+3,341건 적용 중 발견)
1. **401 인증오류의 진짜 원인은 계정차단이 아니라 코드버그였음**: `optimize_11st_product_names.py`의 `_get_session()`이 `_ec._try_cookie_login()`의 반환값(쿠키만료시 False)을 무시하고 그냥 진행 → 로그인 안 된 게스트 쿠키로 hulk API 호출 → 전부 401. 처음엔 "장시간 연속요청으로 계정 이상탐지"라고 오판(몇 시간 기다리니 실제로 풀렸었음 — 그 사이 다른 크론이나 우연한 재로그인으로 쿠키가 갱신됐던 것으로 추정). **진짜 원인은 [[project_11st_cookie_intro_loop]]와 동일한 패턴(쿠키만료→/view/intro)**. `_get_session`에 쿠키로그인 실패시 `_ec._do_login(driver, login_id, acct.password_enc)`(OTP 포함 풀로그인) 폴백 추가 + `_ec._save_cookies`로 갱신 저장하도록 수정해서 해결(2026-07-02). **CrawlerAccount 비밀번호 필드명은 `password_enc`**(암호화 안 된 평문, 이름과 다름 — `login_pw` 아님, 흔한 오타주의).
2. 그래도 **3회 연속 인증실패시 자동중단**은 안전장치로 유지할 것(무한 재로그인 방지, 크롤링 3회실패 원칙).
3. **KC 인증정보 필요 카테고리(장난감 등)**: `detail['certification']['groups']`가 빈 리스트(`[]`)면 PUT이 400 `"이 카테고리는 인증정보를 반드시 입력하셔야 합니다"`로 거부됨. 인증정보를 임의로 채워넣으면 안 되므로 **groups 비어있으면 PUT 자체를 스킵**.
4. **원산지/원재료 데이터 충돌(식품류)**: 기존에 등록된 원재료유형("상품별 원산지는 상세설명 참조")과 원산지코드가 충돌하는 경우 400 `"RAW_MATERIAL"` 에러 발생. 기존 데이터 자체의 문제라 사전 필터링 어려움 — 실패하면 그냥 스킵하고 다음 상품으로 진행(멈추지 않게).
5. 위 제약들 때문에 SEO 키워드 추가처럼 "안 해도 그만인" 보강 작업은 스킵/에러율이 꽤 높을 수 있음(실측 약 30~50%) — 컴플라이언스 수정(트리밍/위험제거)보다 성공률이 낮은 게 정상이니 당황하지 말 것.

**Why:** 15,395건(jinag7460) 작업에서 이 방식으로 API 비용 없이 처리 완료(트리밍 5,865/5,871, 키워드는 진행 중). [[project_11st_jinag7460_name_opt]]
**How to apply:** 다른 계정/플랫폼(지마켓 등)에도 동일 패턴 적용 가능 — "전수 스캔→위험군만 정밀처리→기계적 처리는 스크립트→카테고리 키워드는 연관성 필터" 순서를 기본 틀로 삼을 것. hulk API PUT 전엔 항상 3번 항목(인증정보) 체크 넣을 것.
