작업(특히 장시간 백그라운드 크롤/배치)이 "멈춘 것 같다"고 보고하기 전에 로그 파일 하나의 mtime만 보고 판단하지 말고, DB 최신 레코드/워치독 크론로그/텔레그램 발송이력까지 교차확인해야 한다.

**Why:** 2026-08-23 L코드(도매마트) 조회 작업 점검 시, `/tmp/check_domemart_lcodes.log` 파일이 2.5시간 안 늘어난 것만 보고 "멈춘 상태"라고 사용자에게 잘못 보고함. 실제로는 stdout 버퍼링 때문이었고, DB에는 실시간으로 계속 기록되고 있었으며 10분 워치독 로그도 계속 "실행 중"만 찍혀 있었음. 사용자가 "잘좀하자"며 불만 표시 — 잘못된 경보(false alarm)로 신뢰를 깎아먹음. [[project_progress_reporting_pipelines]] 참고.

**How to apply:** 장시간 실행 작업(크롤러, 배치, 대량처리)의 상태를 점검할 때는:
1. 프로세스 생존 여부(ps)
2. DB의 최신 레코드 timestamp(실제 진행의 1차 증거)
3. 관련 크론/워치독 로그(있다면 이게 더 신뢰도 높음 — 이미 주기적으로 상태검증하는 로직이 있을 수 있음)
4. 원본 stdout 로그 파일은 버퍼링으로 지연될 수 있어 최하위 신뢰도로 취급
이 순서로 교차검증한 뒤에만 "멈췄다/문제있다"고 보고할 것. 하나의 신호만으로 결론 내리지 말 것.

**추가 사례(2026-08-23, 같은 날 재발):** 스마트스토어 미매칭 일괄판매중지(SuspendAllNoMatchView) 점검 때, 로그(`/tmp/suspend_smartstore_nomatch.log`)에 "실패"만 잔뜩 있고 "성공" 문구가 전혀 없다고 해서 "성공 0건, 전량 실패"라고 사용자에게 잘못 보고함. 실제로는 이 로그가 **실패만 기록하고 성공은 로그를 안 남기는 구조**였음(코드: `success += 1`은 로그 없이 카운터만 증가, `log.write`는 예외 블록에서만 호출) — DB를 직접 세보니 실제로는 4,836건 성공, 913건만 진짜 남아있었음(전체 미매칭 조건 재조회로 확인). 사용자가 "일단 내가 다시지시할께"로 대화를 정리 — 연속된 오판으로 신뢰가 흔들림.
→ **일반화된 교훈:** 로그 파일의 "부재"(성공 로그가 안 보임)를 "실패"로 해석하지 말 것. 로그 설계 자체가 무엇을 기록하고 무엇을 기록하지 않는지(성공은 조용히 넘어가는 패턴이 흔함) 코드를 먼저 읽고 확인한 뒤, 최종 결론은 항상 DB의 현재 상태(원래 판단기준과 동일한 쿼리를 직접 실행)로 검증할 것. "로그에 안 보인다" ≠ "안 됐다".
